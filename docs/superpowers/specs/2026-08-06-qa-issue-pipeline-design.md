# QA 이슈 파이프라인 설계

> QA 피드백을 GitHub 이슈로 등록하고, Claude 에이전트가 순차적으로 가져와 수정하는 파이프라인.
> 작성일 2026-08-06 · 범위: 파이프라인만 (자산 QA 하네스는 별건, `docs/QA_HARNESS_PLAN.md`)

---

## 1. 문제

디자이너 2명이 구글시트에 QA 결과를 기록 중이다(238행 체크리스트 기반, 현재 92행 판정 진행). 이 피드백이 시트에만 쌓여 있어 작업으로 이어지지 않는다. 사람이 매번 읽고, 옮겨 적고, 무엇이 처리됐는지 기억해야 한다.

제출 마감이 임박했고 미착수 제출물(영상·PDF 3종)이 남아 있어, QA 처리에 드는 사람 시간을 최소화해야 한다.

## 2. 목표

- 시트의 신규 피드백만 골라 GitHub 이슈로 등록한다 (중복 등록 없음)
- 에이전트가 이슈를 한 건씩 가져와 수정 → PR까지 만든다
- 디자이너가 결과를 확인하고 승인할 수 있다
- QA 과정이 심사위원에게 노출되지 않는다

## 3. 공개 범위 제약

제출 요건상 `debut-loop`은 public이어야 한다(요건 §2-1 "공개 권장", Pages 무료 배포 조건). 그러나 QA 과정 — 미완성 자산 현황, 디자이너 내부 코멘트, Fail 기록 — 은 심사위원에게 보이지 않는 편이 낫다.

**결정: 리포를 둘로 나눈다.**

| 리포 | 공개 | 내용 |
|---|---|---|
| `Sunmi-Park-private/debut-loop` | **public** | 코드, 에셋, 커밋 이력, PR, Pages 배포 |
| `Sunmi-Park-private/debut-loop-qa` | **private** | QA 이슈, Projects 보드. **코드 없음** |

파생 규칙:

- 공개 리포의 **브랜치명·PR 제목에 QA 이슈 번호를 쓰지 않는다.** 증상 기반으로 짓는다.
  - ❌ `qa/issue-12` → ✅ `fix/title-hero-crop`
  - ❌ `fix: QA #12 대응` → ✅ `fix: 타이틀 화면 상단 이미지 잘림 수정`
- 리포가 다르므로 커밋 메시지의 `Closes #12` 자동 close가 동작하지 않는다. `/qa-work`가 명시적으로 닫는다.
- 스크린샷은 private 리포에 두면 인라인 렌더링이 안 되므로 **Google Drive에 업로드하고 링크**한다.

> 예외: `docs/QA-ASSET-CHECKLIST.md`는 "체계적으로 QA한다"는 증거로 **의도적으로 public 리포에 커밋**되어 있다. 이 결정은 유지한다.

## 4. 권한

| 대상 | 권한 |
|---|---|
| 디자이너 2명 | `debut-loop-qa`에 **Write**. 공개 리포에는 권한 부여 안 함 |
| Projects 보드 | 보드 자체를 private로 두고 두 사람을 collaborator로 초대 (보드 public 전환 불필요) |

디자이너는 QA 이슈에서 코멘트·라벨 정리·확인 승인을 하고, 코드는 건드리지 않는다.

## 5. 이슈 대상 선정

시트의 각 행을 판정과 코멘트로 분류한다.

| 조건 | 이슈화 | 라벨 |
|---|---|---|
| `판정 = Fail` | O | `bug` |
| `판정 = ?` | O | `question` |
| `판정 ∈ {N-A, Pass}` **이면서** 코멘트 열에 내용 있음 | O | `enhancement` |
| `판정 = Pass`, 코멘트 없음 | X | — |
| `판정` 빈칸 (미검수) | X | — |

작업 유형 라벨을 함께 붙인다. 이게 없으면 에이전트가 "답변만 필요한 이슈"에 코드를 짠다.

| 라벨 | 의미 | `/qa-work` 동작 |
|---|---|---|
| `qa:code` | 소스 수정 필요 | 브랜치 → 수정 → PR |
| `qa:asset` | 에디터 설정값(배율·좌표) 조정 | 설정 JSON만 변경 |
| `qa:question` | 판단·답변만 필요 | **코드 미변경.** 조사 후 이슈에 답변 |

## 6. 중복 판별

상태 저장소는 GitHub 이슈 하나뿐이다. 로컬 상태 파일을 두지 않는다.

이슈 본문 첫 줄에 HTML 주석 마커를 넣는다:

```
<!-- qa-row: 10 | fail | a3f9c2 -->
```

- `10` — 시트 `#` 열 (안정적인 행 ID)
- `fail` — 판정 (정규화: 소문자, `n-a` → `na`)
- `a3f9c2` — 코멘트 열 텍스트를 정규화(공백 축약·양끝 트림)한 뒤 SHA-1 앞 6자

동기화 시 `gh issue list --state all`로 기존 마커를 전부 수집한 뒤:

| 상황 | 동작 |
|---|---|
| 동일 키 존재 | **skip** |
| 행 번호는 있으나 판정/코멘트가 바뀜 | **새 이슈 생성** + 이전 이슈에 "행 재검수됨 → #새번호" 코멘트 |
| 행 번호 없음 | **신규 생성** |

**한계**: 이슈 등록 후 시트 코멘트의 오타를 고치면 해시가 바뀌어 중복 이슈가 생긴다. → 운영 규칙으로 "등록 후 코멘트 열 수정 금지"를 `docs/qa/README.md`에 명시한다.

## 7. 작업 우선순위

제출 순서상 자산 QA는 **영상 촬영보다 먼저**여야 한다(제출 체크리스트 §5). 영상에 잡히는 화면에서 폴백이 노출되면 안 된다.

`/qa-work`의 선택 순서:

1. `대분류 ∈ {프롤로그, 로딩, 타이틀, 로비, 스토리}` **이면서** `bug` — 영상에 잡히는 화면
2. 나머지 `bug`
3. `enhancement`
4. `qa:question`

Projects 보드에서 Todo 컬럼의 순서가 이 규칙보다 우선한다(사람이 정한 순서를 존중).

## 8. 파이프라인

```
구글시트(체크리스트)          [향후] 하네스 리포트 JSON
        │                              │
        └──────────┬───────────────────┘
                   ▼  /qa-sync (수동 트리거)
          debut-loop-qa (private)
            Issues ──→ Projects 보드
                   │
                   ▼  /qa-work (1건씩)
          debut-loop (public)
            브랜치 → 수정 → 검증 → PR
                   │
                   ▼
          Drive 스크린샷 업로드 → QA 이슈에 결과 코멘트
                   │
                   ▼
          디자이너 확인 → 사람이 PR 머지 → 이슈 close
```

### 8-1. 입력 어댑터

`/qa-sync`는 **정규화된 행 배열**을 받아 동작한다. 소스별 어댑터가 이 형태로 변환한다.

```
{ row, 대분류, 화면, 진입경로, 확인항목, 슬롯ID, 기대결과, 업로드, 판정, 비고, 코멘트 }
```

- **시트 어댑터** — 이번 범위. Google Drive MCP `read_file_content`로 읽어 파싱
- **하네스 어댑터** — 미구현. `scripts/qa-scan.mjs` 출력 JSON을 같은 형태로 변환하면 나머지 로직은 그대로 재사용된다

### 8-2. `/qa-sync`

1. 시트 읽기 → 행 배열로 정규화
2. §5 규칙으로 이슈 대상 선별
3. `gh issue list --repo .../debut-loop-qa --state all --search "qa-row"` 로 기존 마커 수집
4. §6 규칙으로 신규만 필터
5. 생성 전 **대상 목록을 사용자에게 보여주고 승인받는다** (오등록 방지)
6. `gh issue create --repo .../debut-loop-qa` 로 생성, Projects Triage에 추가
7. 결과 요약 보고 (생성 N건 / skip M건 / 재검수 K건)

**이슈 형식**

```markdown
<!-- qa-row: 10 | fail | a3f9c2 -->
**화면**: 타이틀 › 타이틀
**슬롯**: `title-hero`
**진입 경로**: 로딩 종료
**기대 결과**: ①②③⑤ — 화면 전체 cover, 상하 잘림 없음
**판정**: Fail
**디자이너 의견**: 상단 이미지 잘림 현상
**비고**: 권장 1080×2400

_QA 시트 행 #10 · 2026-08-06 동기화_
```

제목: `[QA #10] 타이틀 — title-hero 상단 잘림`

### 8-3. `/qa-work`

1. §7 순서로 Todo에서 1건 선택 → 사용자에게 확인
2. `qa:question`이면 → 조사 후 이슈에 답변 코멘트, 종료 (코드 미변경)
3. 증상 기반 브랜치 생성 (`fix/<증상>`)
4. 수정
5. **검증 게이트**: `npm run typecheck` + `npm test` (110개 유지)
6. 430×800으로 해당 화면 캡처
7. Drive `debut-loop QA/shots/` 에 업로드
8. PR 생성 (QA 이슈 번호 미언급)
9. QA 이슈에 결과 코멘트 — 변경 요약 + PR 링크 + 스크린샷 링크. Projects를 Review로 이동
10. **머지는 사람이 한다.** 다음 `/qa-work` 실행 시 머지된 PR을 감지해 해당 QA 이슈를 close하고 Done으로 이동

## 9. 산출물

| 파일 | 역할 |
|---|---|
| `.claude/commands/qa-sync.md` | 시트 → 이슈 |
| `.claude/commands/qa-work.md` | 이슈 → 브랜치 → PR |
| `docs/qa/README.md` | 팀 사용 안내 (한국어). 운영 규칙 포함 |

`.claude/commands/`는 public 리포에 커밋된다. 파일 안에 QA 리포 이름(`debut-loop-qa`)이 들어가 존재 자체는 드러나지만, private이라 내용은 보이지 않는다. 이는 허용한다 — 오히려 제출 요건 §2-4 "AI 대상 주요 프롬프트 및 지시 사항"의 증거가 된다.

## 10. 사전 준비 (1회)

1. `gh repo create Sunmi-Park-private/debut-loop-qa --private`
2. 라벨 6종 생성: `qa`, `qa:code`, `qa:asset`, `qa:question`, `bug`, `enhancement`
3. Projects 보드 생성 (Triage / Todo / In progress / Review / Done), QA 리포에 연결
4. 디자이너 2명을 QA 리포에 Write로, 보드에 collaborator로 초대
5. Drive에 `debut-loop QA/shots/` 폴더 생성
6. `gh auth refresh -s project` — Projects 조작 권한

## 11. 범위 밖

- **자산 QA 하네스** — `docs/QA_HARNESS_PLAN.md`의 228행 자동 판정. 어댑터 자리만 열어두고 이번엔 구현하지 않는다
- **시트 되쓰기** — Drive MCP가 셀 쓰기를 지원하지 않는다. 현황은 Projects 보드가 정본
- **시트 하단 떠다니는 메모 4건** — 행에 붙어 있지 않아 자동 추출 대상이 아니다. 수동 등록
- **PR 자동 머지** — 사람이 판단한다
